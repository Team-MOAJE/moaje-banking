# 데이터 정합성 8단계 검토 메모

## 반드시 짚고 갈 부분

1. 사용자 경험은 `송금 접수`보다 `송금 완료`에 가깝게 보여주는 것이 자연스럽습니다.
   다만 Redis 가승인만으로 완료를 확정하지 말고, 외부 금융망 성공 응답을 받은 경우에만 `COMPLETED`로 확정하는 편이 안전합니다.

2. ASSET의 Redis 선반영은 좋은 UX를 만들지만, 원장 DB 최종 반영 전까지는 `가용 잔액`과 `확정 잔액`을 구분해야 합니다.

3. BANKING은 외부 금융망 호출 멱등성을 가져야 합니다.
   Kafka 메시지 재전달이나 네트워크 재시도 때문에 같은 이체가 두 번 실행되지 않도록 `eventId`, `transferId`, `externalTransactionId`를 기준으로 중복 처리를 막아야 합니다.

4. 외부 금융망 호출은 성공했지만 완료 이벤트 발행이 실패할 수 있습니다.
   BANKING 쪽 처리 이력을 남기고, 완료 이벤트를 재발행할 수 있는 복구 흐름이 필요합니다.

5. 외부 금융망 동기화는 `created_at` 커서만으로는 부족합니다.
   동일 타임스탬프, 지연 도착, 중복 응답을 고려해 `externalTransactionId` UNIQUE 제약 또는 동등한 검증이 필요합니다.

6. Redis 재조립 시 버전 비교는 좋은 방어선입니다.
   버전의 소유권은 ASSET 원장 쪽에 두고, Redis 갱신은 최신 버전만 반영하도록 얇게 유지하는 편이 좋습니다.

7. 배치 대사는 필수에 가깝습니다.
   Redis, 거래 내역, 원장, 외부 금융망 이력 사이의 차이를 탐지하고 자동 보정 가능 케이스와 수동 개입 케이스를 분리해야 합니다.

## 현재 코드 반영 방향

- `adapter`, `port`, `in/out` 패키지는 제거했습니다.
- 서비스 인터페이스와 서비스 구현체만 남겼습니다.
- 구현체 내부에는 실제 로직 대신 TODO 주석만 남겼습니다.
- 사용자가 직접 컨트롤러, DB, gRPC, Kafka, 목업 뱅킹 API 연동을 붙일 수 있게 비워두었습니다.
